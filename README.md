# Qumran

## Project Overview

Qumran is a project dedicated to processing and converting transcriptions of the Dead Sea Scrolls from their raw text format into structured, TEI-compliant XML. The Dead Sea Scrolls are a collection of ancient religious manuscripts of immense historical and religious significance, providing invaluable insights into the history of Judaism and early Christianity. This project aims to make these important texts more accessible and usable for scholarly research and digital humanities applications.

## File Structure

This section outlines the key files and directories within the Qumran project:

*   `original/dss.txt`: This is the master file containing the combined data of all scrolls before any splitting or individual processing occurs. It serves as the primary source input for the project.
*   `original/scroll/*.txt`: These files represent individual scroll texts.
    *   **Naming Convention**: Each file is named according to the scroll's siglum, for example, `1Q14.txt`.
    *   **Internal Format**: The content within each file follows a specific format: `SIGLUM COLUMN:LINE_NUMBER CONTENT`. For instance, `1Q14 1:1 In the beginning...`. This format facilitates parsing and conversion.
*   `original/scroll/*.xml`: These are the XML versions of the individual scroll texts.
    *   **Generation**: They are generated from their corresponding `.txt` files (e.g., `1Q14.txt` is converted to `1Q14.xml`).
    *   **Basic Structure**: The XML files have a basic structure where sentences are typically enclosed in `<s>` tags, and column and line break information from the source `.txt` files is preserved.
*   `scripts/`: This directory contains all the Python scripts used for processing the text files. These scripts handle tasks such as splitting the master `dss.txt` file, converting `.txt` files to `.xml`, and other text manipulation or data preparation tasks.
*   `.github/workflows/`: This directory holds the GitHub Actions configuration files (in YAML format). These workflows automate various project processes, such as automatically splitting the `dss.txt` file and converting the individual scroll texts into their XML representations whenever changes are pushed to the repository.

## Processing Scripts

This section details the Python scripts used for converting and marking up the scroll texts.

### 1. `scripts/txt_to_s_xml.py`

*   **Purpose**: This script converts individual scroll text files (e.g., `1Q14.txt`) from their plain text format into a basic XML structure.
*   **Input**: An individual scroll file located at `original/scroll/<filename>.txt`.
*   **Output**: An XML file named `original/scroll/<filename>.xml`. The content within this XML file is wrapped in tags to denote sentences (`<s>`), column breaks (`<cb>`), and line breaks (`<lb>`), preserving the structural information from the source file.
*   **Usage**:
    ```bash
    python scripts/txt_to_s_xml.py original/scroll/<filename>.txt
    ```

### 2. `scripts/TEI_reconstruction_markup.py`

*   **Purpose**: This script enhances a basic XML file (typically one generated by `txt_to_s_xml.py`) by adding detailed TEI (Text Encoding Initiative) markup. It is specifically designed to identify and tag textual phenomena such as illegible sections (using `<gap>`), editorial reconstructions (using `<supplied>`), and uncertain or unclear readings (using `<unclear>`).
*   **Input**: An XML file that needs TEI enrichment.
*   **Output**: The script prints the TEI-enriched XML content to standard output. To save this output, you must redirect it to a file.
*   **Usage**:
    ```bash
    python scripts/TEI_reconstruction_markup.py path/to/input.xml > path/to/output_tei.xml
    ```

## Automated Workflows (GitHub Actions)

The project utilizes GitHub Actions to automate key processing tasks. These workflows are defined in YAML files located in the `.github/workflows/` directory.

### 1. `splitdss.yml` (Splitting dss.txt)

*   **Trigger**: This workflow is automatically activated by any push to the repository that includes changes to the `original/dss.txt` file.
*   **Action**: It executes a script that parses the `original/dss.txt` master file. This script splits the master file into individual text files, one for each scroll. These individual files are then saved in the `original/scroll/` directory, following the naming convention `SIGLUM.txt` (e.g., `1Q14.txt`, `4Q22.txt`).
*   **Outcome**: After the splitting process, the workflow automatically commits these newly created or updated individual `.txt` files back to the repository. This ensures that the individual scroll texts are always synchronized with the master `dss.txt` file.

### 2. `convert_txt_to_xml.yml` (TXT to XML Conversion)

*   **Trigger**: This workflow is automatically activated by any push to the repository that includes changes to any `*.txt` file within the `original/scroll/` directory.
*   **Action**: Upon detecting a change in an individual scroll's `.txt` file, this workflow automatically runs the `scripts/txt_to_s_xml.py` script on that specific file.
*   **Outcome**: The script converts the changed text file into its basic XML equivalent (e.g., `1Q14.txt` would be converted to `1Q14.xml`). The workflow then commits this new or updated `.xml` file to the `original/scroll/` directory in the repository, ensuring that the XML representation is kept up-to-date with its corresponding text file.

## Overall Workflow

The project's end-to-end process for converting Dead Sea Scrolls transcriptions into basic XML is largely automated:

1.  **Initial Data Input**: The process begins with the `original/dss.txt` file being populated or updated manually. Alternatively, individual scroll files (`original/scroll/<SIGLUM>.txt`) can be added or modified directly.

2.  **Automated Splitting (if `dss.txt` changes)**: If changes are made to `original/dss.txt` and pushed to the repository, the `splitdss.yml` GitHub Action is triggered. This action runs a script that splits `dss.txt` into individual `original/scroll/<SIGLUM>.txt` files. These files are then automatically committed to the repository.

3.  **Automated TXT to XML Conversion**: The creation or update of any `original/scroll/<SIGLUM>.txt` file (either from the step above or from a direct change) triggers the `convert_txt_to_xml.yml` GitHub Action.

4.  **XML Generation**: This second action runs the `scripts/txt_to_s_xml.py` script on the changed `.txt` file(s). The script generates a corresponding basic XML file (e.g., `original/scroll/1Q14.xml`) for each processed text file. These XML files, containing structural tags like `<s>`, `<cb>`, and `<lb>`, are then automatically committed to the `original/scroll/` directory.

5.  **Further TEI Enrichment (Manual Step)**: At this point, the basic XML files are available. Users who wish to create more detailed, TEI-compliant versions can manually use the `scripts/TEI_reconstruction_markup.py` script. This script takes one of the generated XML files as input and produces an output with enhanced TEI markup (e.g., `<gap>`, `<supplied>`, `<unclear>`). This step is currently not part of the automated workflow and requires manual execution and output redirection.

This automated pipeline ensures that the individual text and basic XML files are kept synchronized with the source data, providing a streamlined process for initial text conversion.

## Manual Processing and Usage

While the GitHub Actions automate much of the conversion pipeline, users can also run the processing scripts manually. This is useful for processing files that are not part of the automated workflow, for testing, or if you prefer a more hands-on approach.

### Converting Text to Basic XML

*   **Script**: `scripts/txt_to_s_xml.py`
*   **Purpose**: Converts a single scroll text file (e.g., `1Q14.txt`) into a basic XML file with sentence, column, and line break tags.
*   **Command**:
    ```bash
    python scripts/txt_to_s_xml.py original/scroll/your_scroll_file.txt
    ```
*   **Output**: The script will create an XML file in the same directory as the input file. For example, if the input is `original/scroll/your_scroll_file.txt`, the output will be `original/scroll/your_scroll_file.xml`.

### Applying Detailed TEI Markup

*   **Script**: `scripts/TEI_reconstruction_markup.py`
*   **Purpose**: Enhances an existing XML file (typically one generated by `txt_to_s_xml.py`) with detailed TEI markup for phenomena like illegible text, reconstructions, and unclear readings.
*   **Command**:
    ```bash
    python scripts/TEI_reconstruction_markup.py path/to/input.xml > path/to/output_tei.xml
    ```
*   **Output**: This script prints the TEI-enriched XML to the standard output. Therefore, you **must** use output redirection (`>`) to save the result into a new file (e.g., `path/to/output_tei.xml`). If you run the command without redirection, the XML output will be printed to your terminal screen, and not saved to a file.

## Future Work

This project has laid a foundational workflow for processing the Dead Sea Scrolls. Several enhancements could further improve its utility and robustness:

1.  **Automate TEI Markup**:
    *   **Suggestion**: Integrate the `scripts/TEI_reconstruction_markup.py` script into the GitHub Actions workflow. This could be a subsequent step in the `convert_txt_to_xml.yml` workflow, or a new, separate workflow triggered by the creation/modification of basic XML files.
    *   **Benefit**: This would provide end-to-end automation from raw text to TEI-enriched XML, reducing manual intervention and ensuring consistency.

2.  **Schema Validation**:
    *   **Suggestion**: Implement a validation step for all generated XML files (`.xml` from `txt_to_s_xml.py` and the TEI-enriched versions). This would involve validating them against a relevant TEI P5 schema.
    *   **Implementation**: This could be added as a step in the GitHub Actions workflows (e.g., using `xmllint` or a Python-based XML validation library) or provided as a separate manual script.
    *   **Benefit**: Ensures the generated XML is well-formed and conforms to TEI standards, crucial for interoperability and scholarly use.

3.  **Error Handling and Reporting**:
    *   **Suggestion**: Enhance the error handling within the Python scripts to provide more informative messages. Additionally, improve the GitHub Actions workflows to better report failures.
    *   **Implementation**: Scripts could use more specific exception handling and logging. Workflows could be configured to send notifications (e.g., email or Slack) upon failure.
    *   **Benefit**: Makes troubleshooting easier and ensures that users are promptly alerted to any issues in the automated processing pipeline.

4.  **Script for Splitting `dss.txt`**:
    *   **Suggestion**: Currently, the `splitdss.yml` workflow mentions executing "a script" to parse `original/dss.txt`. If this script is not yet present in the `scripts/` directory, it should be created and documented.
    *   **Benefit**: Centralizes all processing logic within the `scripts/` directory and makes the splitting process transparent and manually executable if needed.

These potential improvements would make the Qumran project a more comprehensive and reliable tool for working with the Dead Sea Scrolls.
